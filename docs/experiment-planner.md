# Experiment planner

`tools/experiment.py` turns a preregistered JSON specification into deterministic jobs. It prevents a held-out
run from starting with different code, configuration, research context, or data than the version that was sealed.
It automates execution discipline; it does not choose parameters or decide whether a scientific result is a GO.

## Executable specification

An executable spec adds this structure to the existing `sim-experiment-spec-*` format:

```json
{
  "execution": {
    "command": [
      ".venv/bin/python", "-u", "-m", "research.runners.example",
      "--seed", "{seed}", "--phase", "{partition}",
      "--arm", "{arm}", "--out", "{output}"
    ],
    "output": "research/findings/raw/example/{partition}/{backend}/{arm}-{seed}.json",
    "arms": ["control", "treatment"],
    "targets": {
      "numpy": {"device": "cpu", "lane": "pool"},
      "cupy": {
        "device": "cuda:0", "lane": "gpu",
        "env": {"CUDA_VISIBLE_DEVICES": "0"}
      }
    },
    "corpus_check": {
      "path": "research/findings/example-corpus-check.json",
      "sha256": "<sha256 of that file>",
      "query": "Has this mechanism and exact test already been tried?",
      "max_age_seconds": 86400
    },
    "dependencies": ["requirements-extra.txt"],
    "inputs": [
      {"path": "research/config/example.json", "sha256": "<sha256>"},
      {"path": "data/example.npz", "sha256": "<sha256>"}
    ],
    "runtime_outputs": ["research/findings/raw/example/{partition}/{backend}/{arm}-{seed}.log"],
    "claim_stale_seconds": 21600
  }
}
```

The corpus-check file is machine-readable evidence, not a free-form reason string. It must record:

```json
{
  "schema": "sim-corpus-check-v1",
  "experiment_id": "example",
  "query": "Has this mechanism and exact test already been tried?",
  "status": "success",
  "completed_at": 1785820000,
  "rag": {"status": "success", "index_digest": "<catalog/index identity>"}
}
```

The planner rejects failed retrieval, a different query or experiment, a changed digest, and a stale timestamp.
The check's digest is part of every job ID and execution contract.

## What a seal covers

A seal contains an explicit file-by-file manifest of:

- every Python and shell file under `sim/`, `research/runners/`, `experiment/`, and `tools/`;
- `research/__init__.py`, the experiment spec, and the successful corpus-check record;
- standard dependency declarations such as `requirements.txt`, `pyproject.toml`, and lock files;
- every file named by `execution.dependencies`, `execution.inputs`, prerequisites, and existing stop decisions;
- the exact paths allowed to change while the seal is active.

The only built-in mutable paths are the provenance log, the corpus-check history log, every output generated by
the complete backend/partition/arm/seed matrix, each output's provenance sidecar and claim, plus paths explicitly
listed in `runtime_outputs`. Similar-looking neighboring files are not allowed. This lets the authoritative
worktree retain its two append-only logs and lets calibration results land without invalidating held-out work,
while code or config edits still fail the seal.

At launch, `execute-job` rebuilds the code digest, verifies every input, checks the Git revision, and validates the
RAG record again before importing the runner. On a pool archive it also verifies `.source_revision` and every file
in `.source_manifest.sha256`. A plan made in another worktree therefore fails on the canonical GPU checkout or a
pool node when their revision or content differs. Provision all declared specs, configs, data, and dependencies to
pool nodes; a missing file fails closed instead of running stale code.

## Claims and outputs

The launch wrapper creates `<output>.claim` atomically with its job ID, host, process ID, and start time. It removes
the claim after success or ordinary failure. A dead worker's claim becomes recoverable after
`claim_stale_seconds`; a live local process remains protected regardless of age. A completed output always blocks
a rerun. A hard power loss or `SIGKILL` leaves a claim until the stale interval expires.

## Commands

Write seals and plans outside the worktree:

```bash
.venv/bin/python tools/experiment.py seal \
  --spec research/specs/example.json --seal /tmp/example.seal.json

.venv/bin/python tools/experiment.py plan \
  --spec research/specs/example.json --partition calibration \
  --plan-dir /tmp/example-calibration-plan

.venv/bin/python tools/experiment.py plan \
  --spec research/specs/example.json --partition held_out \
  --seal /tmp/example.seal.json --plan-dir /tmp/example-heldout-plan
```

Plan directories and their job manifests are create-only and read-only. GPU and pool commands still enter through
`tools/queue_add.sh`; local jobs run the same verification wrapper directly.

## Limits

The planner cannot discover files opened dynamically by arbitrary runner code. Such data and config must be named
in `inputs` or `dependencies`. It hashes dependency declarations, not the installed contents of the virtual
environment or GPU driver. It verifies integrity with public digests and read-only plans, not a secret signature;
someone with write access to both the plan and command can forge a new plan. Environment values that affect a run
must be declared in the backend target so they become part of the job contract.
