# Path 3 Phase 3.4 — Multi-session continuity test: design

**Date:** 2026-05-11
**Status:** OPEN — design ready, sequenced after Phase 3.3 (real LLM)
**Author:** autonomous arc 2026-05-11

This is the validation plan for the Path 3 distinguishing claim:
**continuous learning without catastrophic forgetting across sessions.**

Phase 3.2 shipped the interface (orchestrator + chat + persistence).
Phase 3.3 swaps in a real LLM. Phase 3.4 tests whether the
combined system actually does what it claims over days/weeks of
intermittent use.

## Hypothesis

A user can bind ~20 facts to `main_hippo` over Day 1, return on Day
3 / Day 5 / Day 7, and recall those facts at ≥ 80% accuracy. Each
session may optionally trigger consolidation. The biology-grounded
sim's "no catastrophic forgetting" property holds at this scale.

Comparison baseline: an LLM with conversation-history-only memory
(no sim layer) loses everything between sessions.

## Test design

### Phase 3.4.1: Single-session capacity (1-2 days work)

Goal: how many facts can the user bind in one session before
accuracy degrades?

Procedure:
1. Bootstrap `main_hippo` (or use existing)
2. Bind 5, 10, 15, 20, 25, 30, 40 facts sequentially (no
   intervening consolidation)
3. Recall every fact at each step (test all previously-bound)
4. Plot accuracy vs n_bound

Pass criteria: ≥ 80% at n=20; ≥ 60% at n=40.

Expected ceiling: ~20-30 with synonym scale; ~50-100 with synonym16
scale.

### Phase 3.4.2: Inter-session retention (3-7 day arc)

Goal: do bindings made on Day 1 survive 7 days of no use?

Procedure:
1. Day 1: bind 20 facts. Run consolidate(3 cycles). Save lineage.
2. Day 3: load lineage. Recall all 20. Record accuracy.
3. Day 5: load. Recall. Bind 5 NEW facts. Consolidate.
4. Day 7: load. Recall all 25. Record.

Pass criteria:
- Day 3 retention ≥ 80% of Day 1 accuracy
- Day 5 retention ≥ 70%
- Day 7 retention ≥ 60%
- New (Day 5) bindings don't degrade Day 1 bindings by > 20%

### Phase 3.4.3: Interference test (1 day work)

Goal: does binding a NEW fact for a previously-bound key (collision)
gracefully overwrite or interfere?

Procedure:
1. Bind "my-pet" → north. Recall. Verify motor_N.
2. Bind "my-pet" → east. Recall. Should now be motor_E.
3. Try recall of related keys ("favorite", "pet" alone) to see
   if collision spilled over.

Pass criteria: rebind shifts top-1; unrelated keys remain stable.

### Phase 3.4.4: Forget then rebind (1 day work)

Goal: does forget() actually free capacity for new bindings?

Procedure:
1. Bind 20 facts, recall accuracy = X.
2. Forget 5 of them (decay=0.0, full erase). Recall remaining
   15: should match X for those 15.
3. Bind 5 NEW facts. Recall total 20: should match or beat X.

Pass criteria: forgotten facts measurably weaker (< 30% confidence);
new facts encoded at similar strength to originals.

## Implementation

### `research/runners/multi_session_test.py` (new, ~300 lines)

CLI:
```bash
python -m research.runners.multi_session_test \
    --lineage main_hippo \
    --phase capacity      # 3.4.1
    --phase retention      # 3.4.2 (records timestamp; load on resume)
    --phase interference   # 3.4.3
    --phase forget         # 3.4.4
    --out research/findings/raw/g11_bg/phase3.4-{phase}.json
```

For phase 3.4.2 (retention, multi-day): the runner saves state +
timestamp; subsequent invocations N days later load and continue.

### `research/runners/multi_session_aggregator.py` (new)

Reads the JSON outputs from each phase and renders a multi-day
graph (accuracy vs days-since-bound).

### Webapp endpoint (optional)

`GET /api/multi-session/{lineage}` returns the aggregated retention
curve from the lineage's growth events. Useful for the dashboard to
show "Day 3 retention: 87%" type panels.

## Open questions

1. **Real-LLM dependency?** Should phase 3.4 use MockLLM (faster,
   deterministic) or real LLM (more representative)? Probably both —
   MockLLM for the engineering tests, real LLM for the
   "user experience" qualitative arc.
2. **Sleep-replay frequency?** Once per session? Every Nth bind?
   Continuous? Likely empirical.
3. **What counts as a "session"?** A chat reset? A new Python
   process? A new day? Probably orthogonal to the persistence
   question — the lineage save/load IS the session boundary.
4. **Vocab growth strategy?** As bindings exceed 8 (synonym tier
   capacity), do we auto-promote to synonym12? synonym16? Tier 3?
   Auto-growth Phase A2 design covers this; need to wire it.

## Why this is important

Path 3's core claim is "biology-grounded memory enables continuous
learning across sessions." Without Phase 3.4 data, that claim is
just architecture — no validation. Phase 3.4 turns the architecture
into evidence.

If the data is positive: Path 3 is real, and we have the answer to
"how do you build an LLM agent with persistent memory across
sessions?"

If the data is negative: we learn what scale of binding the current
sim arch can handle, and where to invest next (consolidation
frequency, sleep cycle count, vocab tier promotion thresholds).

Either outcome is publishable / shippable. That's the right shape
for a research arc.
