# Path 3 Phase 3.3 — Real LLM integration: design

**Date:** 2026-05-11
**Status:** OPEN — design ready, user-blocked on LLM choice
**Author:** autonomous arc 2026-05-11

This is the swap-in design for replacing MockLLM with a real local LLM
in `LLMMemoryOrchestrator`. Phase 3.2 (the orchestrator scaffold +
demo + webapp surface) is fully shipped; this doc covers the actual
LLM integration.

## Decision tree

1. **Pick an LLM** (see comparison below)
2. **Pick a serving backend** (ollama / vLLM / llama.cpp)
3. **Implement an adapter conforming to the orchestrator's
   `llm_callable` signature**
4. **Wire it into `LLMMemoryOrchestrator` constructor**

The orchestrator's interface is unchanged — only the `llm_callable`
argument flips from `MockLLM()` to the new adapter.

## LLM candidate comparison

All candidates are open-weights and CPU-runnable at Q4 quantization.

| Model | Params | Q4 size | Tool-use? | Latency (CPU) | Tradeoff |
|---|---|---|---|---|---|
| **Phi-3-mini-4k-instruct** | 3.8B | ~2.3GB | Strong (Microsoft fine-tuned for it) | ~0.5-2s/turn | Good tool-use bias; small context (4K) |
| **Llama-3.2-3B-Instruct** | 3.2B | ~2.0GB | Native (Meta's official format) | ~0.5-2s/turn | Cleanest tool-call protocol |
| **Qwen2.5-3B-Instruct** | 3.1B | ~2.0GB | Native + structured output | ~0.5-2s/turn | Best multilingual; tool-use solid |
| **Mistral-7B-Instruct-v0.3** | 7B | ~4.5GB | Yes | ~2-5s/turn | More capable but 2x slower |
| **Llama-3.1-8B-Instruct** | 8B | ~5.0GB | Native | ~3-7s/turn | Best chat fidelity in the 7-8B class |

**Recommendation: Llama-3.2-3B-Instruct.** Best speed/quality tradeoff
for this use case. Tool-use is native in the official chat template,
and 3B is fast enough that the bridge ops dominate per-turn time. Phi-3
is the close second; Qwen2.5 if multilingual matters.

## Serving backend comparison

| Backend | Setup | API style | GPU? | CPU? |
|---|---|---|---|---|
| **ollama** | `ollama pull llama3.2:3b` (1 command) | OpenAI-compatible REST | CUDA/Metal | Yes (slow) |
| **vLLM** | `pip install vllm` + GPU | OpenAI-compatible REST | Required | No |
| **llama.cpp + llama-server** | Compile or `pip install llama-cpp-python` | Custom REST or Python binding | Optional | Yes (fast) |
| **Hugging Face transformers** | `pip install transformers torch` | Python only | Optional | Yes (slow) |
| **Direct ONNX runtime** | `pip install onnxruntime` | Python | Optional | Yes (very fast) |

**Recommendation: ollama for v1.** It's the lowest-friction path. One
command installs it, one command pulls the model, and the API is
OpenAI-compatible so we can use the `openai` Python client. The
ollama server runs locally, no cloud dependency.

Fallback if ollama isn't ideal: **llama.cpp via `llama-cpp-python`**.
Python-native, CPU-fast, supports tool-use via grammar constraints.

## Adapter sketch

```python
# sim/llm_adapter_ollama.py (new file, ~150 lines)

from openai import OpenAI
from sim.llm_memory_orchestrator import (
    LLMResponse, ToolCall, TOOL_SCHEMAS,
)


class OllamaLLM:
    """Adapter: ollama (or any OpenAI-compatible API) → LLMResponse.

    Args:
        base_url: ollama API endpoint. Default 'http://localhost:11434/v1'.
        model: ollama model name. Default 'llama3.2:3b'.
        system_prompt: prefix prompt. Defaults to a memory-assistant
            persona that biases the LLM to use the three memory tools.
        timeout_s: per-call timeout. Default 30.
    """
    SYSTEM_PROMPT_DEFAULT = (
        "You are a memory assistant. You have access to three tools:\n"
        "- memory_store(key, value): bind a fact (value must be a "
        "direction word: north, east, south, west, up, down, left, right)\n"
        "- memory_recall(key): retrieve the direction bound to a key\n"
        "- memory_speak(action): get the word bound to a motor pool "
        "(action is N, E, S, or W)\n\n"
        "When the user mentions remembering or storing a fact, use "
        "memory_store. When they ask what they previously stored, use "
        "memory_recall. When they ask what word goes with a direction, "
        "use memory_speak. Always respond in plain English after "
        "consulting the memory."
    )

    def __init__(self, base_url="http://localhost:11434/v1",
                  model="llama3.2:3b",
                  system_prompt=None,
                  timeout_s=30):
        self.client = OpenAI(base_url=base_url, api_key="ollama")  # any key works
        self.model = model
        self.system_prompt = system_prompt or self.SYSTEM_PROMPT_DEFAULT
        self.timeout_s = timeout_s

    def __call__(self, conversation: list[dict]) -> LLMResponse:
        # Build messages with system prompt prepended
        messages = [{"role": "system", "content": self.system_prompt}]
        for m in conversation:
            role = m.get("role", "user")
            if role == "tool":
                # OpenAI format: tool calls referenced by tool_call_id
                # ollama may not support this; for now flatten to assistant
                messages.append({
                    "role": "tool",
                    "name": m.get("name", ""),
                    "content": str(m.get("content", "")),
                })
            else:
                messages.append({"role": role, "content": m.get("content", "")})

        # Wrap TOOL_SCHEMAS into OpenAI tools format
        tools = [{"type": "function", "function": s} for s in TOOL_SCHEMAS]

        resp = self.client.chat.completions.create(
            model=self.model,
            messages=messages,
            tools=tools,
            tool_choice="auto",
            timeout=self.timeout_s,
        )
        choice = resp.choices[0].message

        # Parse tool calls if any
        tool_calls = []
        if choice.tool_calls:
            import json
            for tc in choice.tool_calls:
                tool_calls.append(ToolCall(
                    name=tc.function.name,
                    arguments=json.loads(tc.function.arguments),
                ))
        message = choice.content or ""
        return LLMResponse(message=message, tool_calls=tool_calls)
```

## Wiring

Replace MockLLM with OllamaLLM in three places:

1. **`research/runners/llm_memory_demo.py`** — accept `--llm` flag:
   ```python
   if args.llm == "ollama":
       llm = OllamaLLM()
   else:
       llm = MockLLM()
   ```

2. **`webapp/server.py`** in the `/api/llm-chat` endpoint — same flag-driven
   selection or an env var `SIM_LLM_BACKEND=ollama`.

3. **Test:** keep MockLLM for unit tests (fast); add a real-LLM smoke
   test marked `@pytest.mark.slow` + `@pytest.mark.requires_ollama` that
   skips if ollama isn't running.

## Validation plan

1. **Unit tests** still pass with MockLLM (no regression). All 32
   Phase 3.2 tests should be untouched.
2. **Smoke test** real-LLM against MockLLM with identical scripts —
   compare:
   - Same tool calls dispatched?
   - Same final answers within ~minor variation?
   - Errors propagate identically?
3. **End-to-end demo** with a real LLM running:
   ```bash
   ollama serve &
   ollama pull llama3.2:3b
   python -m research.runners.llm_memory_demo --llm ollama --seed 42
   ```
4. **Webapp smoke** — chat through the dashboard at
   /api/llm-chat with the real LLM behind it.

## Risks + mitigations

| Risk | Mitigation |
|---|---|
| Ollama not installed → import error | Adapter raises clear "install ollama" message; fallback to MockLLM |
| Real LLM gives wrong tool calls (e.g. fabricated keys) | Orchestrator already handles unknown-tool / error wraps; user sees the error |
| Real LLM is slow (~2s/turn) | Acceptable; bridge ops already take ~1-2s for store |
| Real LLM ignores tool schemas | Fall back to MockLLM pattern matching as a "supervisor" — if no tool call but pattern matches, dispatch anyway |
| Multi-turn conversation overflows context window | Phi-3 has 4K, Llama-3.2 has 128K. Truncate older turns past N=20 if needed |

## Open questions

1. **Should the system prompt be tuned per mode?** tier1 vs synonym
   vs synonym12. Different vocabs warrant different tool descriptions.
2. **Should we cache the LLM response per (conversation hash)?**
   Probably yes — same conversation → same answer. Cuts per-turn cost
   for repeated dev cycles.
3. **Should we add streaming for the dashboard?** Server-sent events
   could surface the LLM response as it's generated, but adds complexity.
4. **Should we benchmark MockLLM vs OllamaLLM on the same script?**
   Useful for the user to see the quality jump.

## Why this design is one-line swap-in

The Phase 3.2 work decoupled three things:
1. **Protocol** (TOOL_SCHEMAS) — fixed
2. **Orchestrator** (LLMMemoryOrchestrator) — fixed
3. **LLM implementation** (`llm_callable`) — plugin

The MockLLM and OllamaLLM are both `Callable[[list[dict]], LLMResponse]`.
Anything that fits that signature plugs in.
