# The GNW-bus row family's `retire_status` was stale — two of the three "RETIRABLE_NOW" rows never needed retiring, the third already had it

## Why this is a Wall-2 finding, not a re-run of old work
The owner steer for this session was "retire all the scaffolds we can and make scaffold retirement a first-class citizen." The ledger's own `retire_status` column (`docs/PRODUCTION_INTEGRATION_LEDGER.yaml`, added 2026-09-02, enforced by `tools/gates/production_integration.py` Check D) is the mechanism that makes retirement first-class — a `RETIRABLE_NOW` cheat ages out and BLOCKS after 14 days, forcing the retirement instead of letting it sit. That mechanism is only as honest as its seeding. Auditing the shortlist it names (its own top-of-file note: *"The genuine RETIRABLE_NOW pool is gnw-bus-shadow (+ gnw-two/three-organ-bus, which share its gate_via_bus dead-code follow-on)"*) against the actual source turned up that the note was itself wrong for all three rows it names — the exact kind of drift the retire_status column exists to prevent from going unnoticed.

## What the 2026-09-02 seeding said
All three rows carried:
```
scaffold_retired: NO
retire_status: "RETIRABLE_NOW 2026-09-02"
```
with a comment describing the host `if recalled == p` combination as "COMPUTED-then-OVERRIDDEN, not removed... Full retirement = a ChatBrain.gate_via_bus that never computes the host combination (the named follow-on, design §3)."

## What is actually true, checked against source + re-verified live (2026-09-03, HEAD `482a24fcd`)

**1. `gnw-bus-shadow`.** The `gate_via_bus` follow-on the row calls a still-open TODO was already built and committed same-day, 2026-08-13, commit `6ab22eb55` ("research: GNW-bus SCAFFOLD-RETIREMENT — gate_via_bus never computes the host combination on the covered class"), earning finding `2026-08-13-gnw-bus-scaffold-retirement-SCOPED.md` with a call-count proof: on a covered stored recall, `_substrate_recall` and `_gate_router_combine` are each called **0 times** (`research/findings/raw/_gnw_bus_shadow/scaffold_retire_verify.json`: `go: true`, `n_identical: 22`, `n_total: 22`, `covered_host_combination_computed: false`, `lesion.attribution_to_ignition: 1.0`). `git log -- webapp/gnw_bus_shadow.py` shows exactly 3 commits total, the last being `6ab22eb55` — the file has not moved since. The current `research/runners/brain_chat_tui.py` (read at HEAD, lines 702-756) still carries this exact factoring: `gate_extract` does "EXTRACTION + SIDE-EFFECT phase... WITHOUT the covered-class recall-COMBINATION verdict", and its own docstring says "in gate_via_bus the host `if recalled == p` is never computed for it." The 2026-09-02 seeding pass evidently did not check this already-landed follow-on before writing `RETIRABLE_NOW`.

**2. `gnw-two-organ-bus` and `gnw-three-organ-bus`.** These were never in the state the seeding described. Reading `webapp/gnw_two_organ_bus.py::two_organ_gate_via` and `webapp/gnw_three_organ_bus.py::three_organ_gate_via` directly (both built AFTER `gnw-bus-shadow`'s retirement landed) shows each already consumes `chat.gate_extract` (not the full `gate()`) and calls `chat._gate_router_combine` **only** on the out-of-scope branches (`mode == 'router'`, `mode == 'decline'` with anaphora, or the covered-class veto-then-anaphora fallback) — never on a covered `'route'` commit. Both docstrings say so explicitly ("mirroring `gnw_bus_shadow.gate_via_bus`'s / `gnw_two_organ_bus.two_organ_gate_via`'s routing EXACTLY"). There is no separate "flip-then-override" commit for either — `git log` shows their construction commits (`16ff7efc9`, `a848f27c2`) already carry this shape. The RETIRABLE_NOW status assumed they shared gnw-bus-shadow's OLD pre-follow-on pattern without checking their own source.

## The ledger correction (docs/PRODUCTION_INTEGRATION_LEDGER.yaml)
All three rows: `scaffold_retired: NO -> PARTIAL`, `retire_status: "RETIRABLE_NOW 2026-09-02" -> "BLOCKED:neural-render"`. PARTIAL (not YES) because the host `QuestionRouter`/`_gate_router_combine` is correctly kept for the out-of-scope classes the bus never claims (self/identity, open-ended generation, acquisition, the anaphora-abstain fall-through) — the exact same shape the ledger already uses for `content-selection`'s own PARTIAL row (its residual: "Router still handles self/identity + the anaphora fallback"). `BLOCKED:neural-render` (not a fresh `RETIRABLE_NOW`) because the genuine remaining residual — `gate_extract`'s (agent, action) comprehension is still the host neural-parser/heuristic, and (for the three-organ row) organ C's toy-cue-lexicon competence boundary — is the same neural-comprehension/neural-language frontier every sibling PARTIAL row (`content-selection`, `in-loop-learning`, `open-ended-generation`) already cites. `tools/gates/production_integration.py` Check D accepts `BLOCKED:neural-render` as a valid non-dangling frontier (10 other rows already point at it; `neural-render` itself carries `on_by_default: NO`, satisfying Check D's "genuinely not yet in the production default" requirement). Ran `python tools/gates/production_integration.py`'s `selftest()` (0 failures) and `check(['docs/PRODUCTION_INTEGRATION_LEDGER.yaml'])` against the edited file (0 problems) before committing. `headline.scaffold_retired` (the YES-count ratchet) is unaffected — it stays at 1 (`one-brain-substrate` only); PARTIAL does not count toward it.

## What this is and is not
This is a documentation-accuracy correction, not a capability change — no `sim/`, `webapp/`, or `research/runners/brain_chat_tui.py` file was edited (only a new, additive, `--out`-taking verify runner was added, following the repo's `-m research.runners.X` provenance convention). The value is specifically to Wall 2 ("make scaffold-retirement first-class"): a `retire_status` column that can itself drift out of sync with source (assuming the "same-family" rows share one row's earlier problem, without checking) undermines exactly the forcing function it exists to provide — a stale `RETIRABLE_NOW` would have aged past 14 days (2026-09-16) and BLOCKED commits with a demand to "retire" something that had no work left to do, or worse, invited someone to go delete `_gate_router_combine` entirely (which is still load-bearing for the out-of-scope classes) to satisfy the gate.
