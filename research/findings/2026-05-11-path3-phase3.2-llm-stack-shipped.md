## What this is

The closure of the Path 3 scaffold work that landed earlier today:

```
USER MESSAGE
    ↓
MockLLM (regex pattern recognition)
    ↓
ToolCall(memory_store / memory_recall / memory_speak)
    ↓
LLMMemoryOrchestrator.chat()
    ↓
BridgeMemory.store / recall / speak
    ↓
chat_repl.learn_word_pairing / chat_inference / generative_inference
    ↓
SimulationBridge (real biology-grounded spiking sim)
    ↓
BridgeLineage (atomic save → bridges/lineage/<name>/)
    ↓
TOOL RESULT
    ↓
MockLLM formats final user-facing response
    ↓
USER SEES "Your answer is north." / "Got it. I'll remember: ..."
```

All seven layers of indirection are real (no mocks below MockLLM). The
LLM treats the bridge as a black-box key-value store with the unique
property of continuous learning + no-catastrophic-forgetting + persistent
state.

## Components shipped

### sim/llm_memory_orchestrator.py (347 lines)

- **`TOOL_SCHEMAS`** — three OpenAI-compatible JSON tool schemas:
  - `memory_store(key, value)` — bind a fact via embodied-Hebbian
  - `memory_recall(key, top_k=4)` — W→A inference
  - `memory_speak(action, top_k=4)` — A→W generative
- **`ToolCall`** + **`LLMResponse`** — dataclasses for the protocol.
- **`MockLLM`** — regex-based pattern recognition; recognized patterns:
  - `"remember that <key> is <direction>"` → store
  - `"<key> is <direction>"` → store (with optional "my")
  - `"what's my <key>"` / `"what is my <key>"` → recall
  - `"what word goes with <direction>"` → speak
  - Direction synonyms: up=north, down=south, left=west, right=east
  - Fallback: helpful "I don't understand" message
- **`LLMMemoryOrchestrator`**:
  - `chat(user_input)` drives the tool-use loop
  - Tool-call iterations capped at `max_tool_iterations` (default 5)
  - `_dispatch_tool()` wraps memory ops with `{"error": str(e)}` on
    failure; MockLLM propagates errors back to the user verbatim

### research/runners/llm_memory_demo.py (~280 lines)

End-to-end demo. Build tier1 toy bridge (208 neurons, 3438 synapses),
wrap in BridgeMemory + LLMMemoryOrchestrator, run scripted 5-turn chat.

```bash
SIM_BACKEND=numpy python -m research.runners.llm_memory_demo \
    --seed 42 --lineage llm_demo --out demo.json
```

Sample output:
```
USER:      Remember that my favorite is north.
ASSISTANT: Got it. I'll remember: favorite = north.
  (tool: memory_store, 1.20s)

USER:      What's my favorite?
ASSISTANT: Your answer is west.   <- toy-scale noise
  (tool: memory_recall, 0.03s)
...
```

5 tool calls dispatched across 15 messages, 4 lineage growth events
recorded. Demo proves the **protocol**, not the science accuracy. For
real W→A binding, use mode="synonym" with `--n-events-per-direction
400` (Tier 2.1 8-word vocab: 5/6 W→A aligned, 6/6 A→W).

### webapp/server.py (3 new endpoints)

```
POST /api/llm-chat
  body: {lineage, mode, message, reset_conversation?}
  returns: {response, tool_calls[], conversation_length, n_turns}

GET /api/llm-chat/{name}/transcript?mode=...
  returns: {messages[{role,content}], n_turns, total_messages}

POST /api/llm-chat/{name}/reset?mode=...
  returns: {reset: bool}
```

In-process orchestrator cache keyed by (lineage, mode) tuple. First
call pays the bridge-load cost; subsequent calls fast.

### webapp/static/app.js — `renderLLMChatPanel`

Renders below the bridge-memory bindings in the Lineages tab. Mode
selector, color-coded message log (user / assistant / tool / error),
input box + Send / Enter, Reset button. Auto-loads transcript when
mode changes or lineage is revisited.

## What's open

### Phase 3.3 — real LLM integration (user-blocked)

Open decisions:
1. **Which LLM?** Phi-3-mini / Llama 3.2 / Qwen2.5 (all ~3B Q4, ~2GB).
2. **Which serving backend?** ollama (easy) / vLLM (fast) / llama.cpp (CPU-only).
3. **Where does it run?** Local box / cloud / both.

The orchestrator interface is fixed; the swap-in is one line:
```python
orch = LLMMemoryOrchestrator(memory=mem, llm_callable=real_llm_callable)
```

### Forget + consolidate real-ops (deferred)

BridgeMemory.forget() and .consolidate() are still stubs. Real
implementations:
- `forget(key)` → bridge.set_pathway_weights(key_pathway, weights ×
  decay_rate) for the language_input → motor edges associated with
  the key.
- `consolidate(n_sleep_cycles)` → wire to Phase 1.3 hippocampus
  consolidation path (requires `--enable-hippocampus-consolidation`
  in the underlying bridge build).

Neither is blocking for the user-facing chat — the lineage growth
events DO record both operations, so the audit trail is intact.

### Better-trained lineages for chat UX

The dashboard chat panel works mechanically, but the underlying tier1
toy bridge gives noisy answers (208 neurons, n_events=50 per
binding). For real W→A demonstrations:

```bash
# Train an 8-word synonym lineage (Tier 2.1, 6-20 min on CPU)
python -m research.runners.chat_repl \
    --mode synonym --lineage main --from-scratch \
    --seed 42 --n-train-events 400

# Then chat via dashboard at /api/llm-chat with mode='synonym'
```

This gives the user a real biology-grounded conversational sim with
5/6 W→A aligned + 6/6 A→W aligned per the 2026-05-06 Tier 2.1
breakthrough.

## Strategic value

This shipping arc closes the Path 3 *interface* question. The
biology-grounded sim now has a clean LLM-callable shape:

- **A schema** (TOOL_SCHEMAS) any OpenAI-compatible LLM understands.
- **A protocol** (LLMMemoryOrchestrator) any LLM can drive.
- **A surface** (POST /api/llm-chat) any frontend can hit.
- **A test bed** (MockLLM) for protocol verification without LLM cost.

When Phase 3.3 swaps in a real LLM, none of the rest of the stack
changes. That's the value of doing the orchestrator scaffold first.
