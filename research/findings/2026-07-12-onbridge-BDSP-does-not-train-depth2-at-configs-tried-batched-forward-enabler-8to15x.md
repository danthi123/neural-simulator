## The batched forward (the enabler) — 8–15× speedup, correctness OPEN
`research/runners/_batched_onbridge_forward_derisk.py`: evaluate M examples as M DISJOINT block-diagonal copies of the net on ONE bridge (M examples advance in ONE `_run_one_simulation_step`, amortizing the per-call overhead M×; the RF composer proved disjoint slices don't cross-talk).
- **SPEEDUP: 8–15× confirmed** (M=8: 79 → 6 ms/example; M=16: 8.9×). The per-call Python overhead of the step pipeline IS the numpy bottleneck, and batching amortizes it — a real, large lever.
- **CORRECTNESS: MISMATCH (max|batched−serial| ≈ 0.15), characterized as PRESENCE-COUPLED (per-step global op), UNRESOLVED.** Six hypotheses ruled out (each still mismatches): OU background noise (`enable_ou_process=False`), threshold homeostasis (`enable_homeostasis=False`), default Watts-Strogatz connectivity (`inject_explicit_wiring` REPLACES it — line 2429, so no cross-copy edges), structural plasticity (`enable_structural_plasticity=False`), per-copy init RNG (copy 0 mismatches too), parameter heterogeneity (`enable_parameter_heterogeneity=False` — still mismatches). **The decisive PRESENCE diagnostic** (drive ONLY copy 0, all other copies fully SILENT, vs a lone 1-copy bridge): copy 0 still shifts by **|Δ|=0.105** ⇒ the coupling is **PRESENCE-based, NOT activity/synaptic/init** — a per-step GLOBAL operation over all neurons (a count/population reduction that changes when silent neurons are merely present). The block-diagonal architecture fundamentally shares the ONE bridge's global step ops across copies. **Follow-on (well past the 3-fix wall → a fresh approach, not more guessing):** either (a) bisect the step pipeline to find the specific count/population-reduction op and localize it per-region (likely a small additive/guarded `sim/` edit — legitimate, it makes a global op region-aware for co-resident nets), or (b) switch to true batch-dim vectorization of the forward (each example in its own batch slot, global ops applied per-slot) — a bigger but coupling-free architecture. ## UPDATE (2026-07-12) — root traced to n_total-dependent INIT; block-diagonal is the WRONG architecture (systematic-debugging step-back)
A single-step per-array probe localized the divergence to `cp_membrane_potential_v`, and it is present ALREADY BEFORE the step: copy-0 `v_init` = −61.88 mV in a 1-copy bridge vs −63.33 in a 2-copy bridge. `v_init` = the per-neuron reset potential `vr`, and the bridge draws its per-neuron init over ALL n_total, so the M-copy's copy-0 init differs from a lone 1-copy net (then amplifies through the nonlinear spiking to ~0.10 on E). The earlier "PRESENCE-coupled global op" reading was this init mismatch, not a step op.

**11+ isolation attempts did NOT fix it** (OU off, homeostasis off, WS-connectivity is replaced, structural plasticity off, heterogeneity off, inhibitory-split off, tiling copy-0's own block, and finally **cloning the 1-copy REFERENCE net's full cp_ state into every copy** — still ~0.16). Per systematic-debugging Phase 4.5 (3+ fixes failed → question the architecture, don't keep fixing): **block-diagonal copies on ONE shared bridge is the wrong architecture** — it fights the bridge's n_total-dependent init/RNG (the cloned reference must miss some non-1D/derived init source, or the step re-derives from an uncloned array).

**The correct enabler (the follow-on build):** true **batch-dim vectorization** — a `[batch × neurons]` forward where each example is independent by construction and per-neuron init is identical per slot — or a stripped per-example fast-path for the eval forward. The 8–15× speedup proves the lever is worth that build; the block-diagonal shortcut is retired. A separate numpy-backend bug (`np.asnumpy` in a flag-disable path) surfaced in passing.

## RESOLVED → GO (2026-07-12) — the batched forward WORKS; root was unseeded trait randomization (the block-diagonal architecture was right)
The a0 read found it: `cp_traits = cp.random.randint(0, cfg.num_traits, ...)` (bridge.py:1163) assigns each neuron a TYPE from a **bridge-internal RNG NOT tied to `actual_seed_used`**, and type → `vr` (reset potential, bridge.py:2078) → `v_init`. So two same-seed builds get DIFFERENT `vr` (verified: |Δvr|=25 mV between two seed-42 1-copy builds), which is why every clone/tile failed — there was no reproducible reference to match. **Fix: `cfg.num_traits = 1`** → all neurons trait 0 → identical deterministic `vr` → the block-diagonal batched forward is **EXACT** (max|batched−serial| = **0.00**, presence-coupling 0.00) and **faster: 13× (M=8), 8.5× (M=16), 5.1× (M=32), 2.2× (H96)** — the speedup shrinks as M/net grow (the M-copy bridge's compute offsets the per-call-overhead amortization; the sweet spot is moderate M at small nets, and a training loop amortizes the one-time build so the forward-only speedup is higher). **The block-diagonal architecture was CORRECT all along** — the "wrong architecture" verdict was the unseeded `vr`; the 11+ isolation attempts were all chasing that one non-reproducible value. **Bonus finding:** `num_traits>1` makes the on-bridge net's `vr` build-to-build **non-reproducible** — a real reproducibility issue for any on-bridge result; `num_traits=1` (homogeneous, reproducible) is the clean default for these de-risks. **⇒ the enabler is GO:** the lr×epochs×stability sweep of the BDSP depth-2 net + the dendritic D2 are now iterable at 2–13×.
