# Stage 1.5: the real captured-code correlation is cos ~0.80 — de-risking items 2 and 3

**One line:** Before the load-bearing migrations (spiking cleanup; grounded capture), measure the correlation of the
codes the composer actually faces. The existing `denoise64` codes — which ARE captured concept-pool activity — sit
at **between-cos ~0.80** (mean; max ~0.88), multi-seed. That is far harder than the cos-0.05 production-*scheme*
codes the V=320 capability matrix was validated on, and it predicts that item 3 (grounded capture) will produce
~0.80 codes where two-attribute composition regresses to a boundary.

## Measurement

`load_concepts(seed, 800)` (the composer's own grounded-code path) on the shipped `denoise64` cache:

| seed | V | captured between-cos (mean / max) |
|---|---|---|
| 42 | 16 | 0.820 / 0.873 |
| 43 | 16 | 0.794 / 0.876 |
| 44 | 16 | 0.806 / 0.877 |

These are the codes the composer uses today — captured concept-pool activity, highly correlated (~0.80). For
contrast, the V=320 capability matrix (rungs 1–3) used the production *scheme* codes (`generate_sparse_patterns` +
projection), which are cos ~0.05 — two-attribute resolved there. The gap matters: two-attribute was a *boundary* at
V=16 on these same cos-0.80 codes (the consolidation's documented K=5 boundary), so the V=320 cos-0.05
"two-attribute resolves" result was the EASY end, not the regime real captured codes live in.

## Result — my prediction was WRONG (the honest correction)

I predicted two-attribute would regress to a *fundamental* boundary under captured (cos-0.80) codes. The ρ=0.80
capability matrix (V=320, seed 42) **falsified that**:

| category | D=800 (composer default) | D=2048 |
|---|---|---|
| flat | 4/6 | 6/6 |
| one-attribute | 2/6 | 6/6 |
| two-attribute | 2/6 | **6/6** |
| negation/yes-no | 9/12 | 12/12 |
| clause | 0/6 | 2/6 |

Two corrections:
1. At cos-0.80, **D=800 degrades EVERYTHING** (even flat drops to 4/6) — not just two-attribute. The composer's
   default D=800 is simply insufficient for captured-correlation codes at 320 words.
2. At **D=2048, two-attribute RESOLVES (6/6) even at cos-0.80** — it is NOT a fundamental boundary. Everything
   recovers except the recursive clause (2/6, which needs still more D).

**The unifying insight:** the cost of high code correlation is **dimensional, not capability-specific**. The V=16
two-attribute "boundary" (cos-0.80, D=800), the V=320 clause boundary (cos-0.05, D=800), and this cos-0.80
degradation are the SAME phenomenon — the composer is dimension-bound, and high correlation / composition depth /
vocabulary all draw on one budget, D.

**Multi-seed + D=4096 confirm both halves.** D=2048 ρ=0.80 is multi-seed (42/43/44): flat / one-attribute /
two-attribute 6/6, negation 12/12, clause 1–2/6 every seed. And clause is dimensional too — at **D=4096 clause
climbs to 4/6** (from 1–2/6 at D=2048), so the recursive case keeps recovering with more dimensions (the deepest
composition just needs the most). Nothing in this arc is a fundamental capability boundary; it is all the dimensional
budget.

## What this means for items 2 and 3 (concrete)

- **The grounded 320 agent must use D=2048, not the D=800 default.** At captured-code correlation (~0.80), D=800
  cannot even hold flat memory at 320; D=2048 carries flat / one-attribute / two-attribute / negation. The cos-0.05
  production-scheme codes hid this — they worked at D=800. So the headline operating point for the grounded agent is
  **D=2048**.
- **Item 3 (grounded capture) is now predictable and benign:** at D=2048 the fully-grounded agent carries the whole
  matrix except clause (clause needs D>2048). Two-attribute is NOT lost under real codes — it just needs the
  dimensions, which D=2048 supplies.
- **Item 2 (spiking cleanup) target is now precise: cos-0.80 at D=2048** (the harder, larger regime, not the easy
  cos-0.05 D=800). The rf TPAM precedent was at full 320 vocab; 0.80 correlation + D=2048 is the point to confirm.
- The **decorrelation option** (ZCA) is now framed as an *efficiency* lever, not a 2-attr rescue: decorrelating
  cos-0.80 codes toward cos-0.05 would let the grounded agent run at the cheaper D=800 instead of D=2048. Flagged for
  item 3 / B.

## D is not a dial to minimize — operate high (the reframe)

A fair question raised mid-arc: if higher D consistently fixes everything, why report D=800 at all? **It is not an
operating point.** D=800 is the inherited composer default (what `denoise64` was built at) and the low end of a
measurement sweep — nothing more. The grounded agent **operates at D=2048** going forward: more capable AND more
biologically faithful (real cortical concept ensembles are high-dimensional; ~16K neurons is trivial on the GPU).
D=800's only value was the *contrast* that revealed the dimensional law — you can only show "the cost is dimensional"
by sweeping dimension. The forward rule: **operate at high D; sweep D only to** (a) characterize the scaling law for
larger vocabularies (the rule looks like D ∝ vocab × correlation × composition-depth), (b) find the *minimum
sufficient* D for the shared neuron budget when parser + composer + dlPFC + cleanup all live on one bridge (item B),
or (c) decide whether decorrelation is worth it (lower correlation buys back D). The deliverable is the *efficient*
D, never the *low* D.
