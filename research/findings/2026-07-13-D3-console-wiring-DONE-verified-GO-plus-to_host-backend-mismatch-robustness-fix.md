## A genuine robustness fix found in passing: `sim/backend.py::to_host` (backend mismatch)
Running the smoke on the WRONG backend (the CuPy default, without `SIM_BACKEND=numpy`) crashed in `rf_read_phases` (`sim/bridge.py:5722`): `np.asarray(_backend_to_host(self.cp_rf_spike_step))` → `TypeError: Implicit conversion to a NumPy array is not allowed`. Root cause (systematic-debugging): **`to_host` converted by the ACTIVE backend (`get_backend()`), not the ARRAY TYPE** — so a CuPy (device) array that outlives a mid-process backend switch to numpy (which a CPU sub-brain triggers) was returned UNCHANGED (the `name != "cupy"` branch), then reached `np.asarray()` and raised. **Fix:** convert by array type — `if hasattr(arr, "get"): return arr.get()` (matches the module's own line-60 defensive fallback). This is **byte-identical in BOTH consistent-backend cases** (a numpy array has no `.get()` → returned unchanged; a cupy array → `.get()`, as before); only the backend-mismatch case changes (from a broken device array to a correct host copy). Verified: backend unit tests 37/37 pass, the numpy smoke stays GO, the conversational tests (`test_one_brain_composer_agent` + `test_brain_conversational_agent`) 7 pass. **Honest scope:** this closes a latent to_host fragility (any mixed-backend `to_host` consumer); it does NOT make the whole numpy-designed tiny-demo run on the CuPy backend (that mis-invocation is mixed-backend end-to-end and crashes further downstream at a cupy kernel — run the smoke with `SIM_BACKEND=numpy` per the docstring). A minimal, safe, protected-`sim/` robustness edit (genuine bug, byte-identical when the backend is consistent).
